A frame of bytes, an answered request, and the gate between them

Raw TCP, an eight-byte header, and a router that dispatches on the message id inside it. The part worth drawing is where the session is checked: not once at the start of a connection, but on every message that needs one.

TCP :8999 · frame = msgId(uint32 BE) | length(uint32 BE) | payload · msgIds 1000–1100 · one live session per account, kept in Redis
Why the header carries the length

Without it a reader has to scan for a delimiter it cannot know, and a truncated body cannot be told from a slow one. Eight bytes of framing is what makes "read exactly this many bytes" possible.

Why the gate is per message

An auth message by definition arrives without a session, so a gate at connection time would have to special-case them anyway. Naming the property per message is the same rule with fewer branches.

Why one session, in Redis

Redis holds the live connection id because it has to be shared by every instance that might receive the next frame, and because a session that survives a process is the difference between a takeover and a locked account.
